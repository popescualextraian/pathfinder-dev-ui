# Task 019: Start a plain task on a work item

Status: approved by HD (2026-10-21, in chat: "approved, start the task"); one task, in the checkout (no parallel task)

## Goal

On a work item, "▶ Workflow" starts a multi-step workflow. In practice superpowers already does
plan, build and test inside one step, so the later steps had nothing left to do (HD: "why am I
even using this flow, superpowers already does all"). HD wants a simpler start: **one plain task,
linked to the work item, with a short kickoff prompt that waits for HD's feedback**. HD then steers
it in the task screen (chat, new sessions, ...). The work can be anything: analysis, thoughts,
tests, code.

## Decisions (HD, in chat, 2026-10-21)

- **One active task per item**, counting workflow runs and plain tasks together. No parallel work
  on one item.
- **The card stays where it is.** Starting a plain task moves no lane, and nothing moves later.
- **Start from the item**, not from the sidebar: a "▶ Task" button on the backlog card and in the
  item detail opens the existing New task dialog, prefilled. The user can change the title, prompt
  and model (and the repository, as in that dialog) before starting.

## Design

### What the user sees

- **The button.** "▶ Task" (aria "Start task on #<id>") sits next to "▶ Workflow" in
  `WorkflowControls`, on the card and in the detail.
  - It is shown when the item has no active run. Unlike "▶ Workflow", it does not need any
    workflow definitions.
  - It is available only where workflows are on today (`workflowsOn`: workflows and backlog
    enabled), because the link uses the workflow runs.
- **The dialog.** The existing `NewTaskDialog`, opened with initial values:
  - Title: `#<id> <title>`
  - Prompt: the default kickoff prompt (below), editable
  - Model: empty (the default)
  - Repository: as the dialog picks it today
  - Heading: "New task on #<id>"
- **Default kickoff prompt** (built in the frontend from the item; fixed in code for now):

  ```
  We plan to work on backlog item #<id>: <title>

  <description>

  <url>

  Read it and get familiar with it, then wait for my instructions. Do not change anything yet.
  ```

  Leave out empty lines for a missing description or url.
- **After the start**, the app opens the task screen of the new task, as the sidebar's New task
  does (AD's call: that is where the user works with it).
- **The link.**
  - The card and the detail show a run line for the item: "Task · <state>" and **■ Stop**. A
    plain task has no step, no Continue and no step list.
  - The task screen shows its item as it does for a workflow run today (`runByTask`).
  - **Stop** ends the link only. The task is left as it is, as Stop does for workflow runs today.
    After that, "▶ Task" and "▶ Workflow" show again.

### Backend

- **The link is a workflow run of kind `task`** (AD's call). This gives a plain task the
  workflow runs' storage, stream, one-active-per-item rule, Stop and "task gone → failed" for
  free.
  - `WorkflowRun` gets an optional `kind: 'task'`; absent means a workflow run. Existing run
    files load unchanged.
  - A run of kind `task` has no workflow to follow. The builder decides the representation (for
    example a synthetic one-step definition titled "Task", or optional `workflowId`/`definition`),
    as long as the views and the stored runs stay simple and old runs keep working.
- **The runner and a plain-task run:**
  - it creates the task with the given title, prompt, model and repository;
  - it moves no stage and starts no session or step, and sends no exit prompt;
  - state: `needs-you` while the task has an open question or a failed or interrupted session
    (the same rule as today), otherwise `running`;
  - it is never `done` by itself. It ends by Stop (`stopped`) or when the task is gone (`failed`,
    as today);
  - `advance` refuses it with 409.
- **The API:** `POST /workflow-runs/task` with `{ itemId, prompt, title?, model?, repository? }`.
  - 201 with the run view;
  - 400 on invalid input (DTO validation, as the other endpoints do);
  - 404 for an unknown item;
  - 409 when the item has an active run.

  The prompt is required and not empty. The title defaults to `#<id> <title>`.
- **Repository:** `WorkflowTaskStart` gets an optional `repository`, passed through by the
  integration adapter. Workflow runs keep starting on the default repository, as today.
- **Layers:** the controller in `api/workflows`, the logic in the workflow service package. The
  workflow package still imports only `commons`.

### Not in scope (to the backlog)

- choosing a work item in the sidebar's New task dialog;
- editing the default kickoff prompt (per project or in settings);
- several active tasks per item;
- moving the card when a plain task starts or ends.

## Steps (test-first, a commit per step)

1. **Backend: plain-task runs.**
   - Runner unit tests:
     - start creates the task with the given title, prompt, model and repository, and moves no
       lane;
     - 409 with an active run of either kind, and a workflow start is refused while a plain-task
       run is active;
     - 404 for an unknown item;
     - the run stays `running` after the task's first turn ends idle;
     - `needs-you` on an open question;
     - Stop gives `stopped` and leaves the task;
     - a task that is gone gives `failed`;
     - `advance` gives 409;
     - an old run file without `kind` still loads and runs.
   - Then the runner and the model.
2. **Backend: the endpoint.** Controller tests for 201/400/404/409, then `POST
   /workflow-runs/task` and the `repository` pass-through in the adapter.
3. **Frontend: "▶ Task".**
   - Testing Library tests:
     - the button shows without workflow definitions and hides while a run is active;
     - the dialog opens prefilled (title, kickoff prompt with the item's fields), and the edited
       values are what is sent;
     - after the start the app opens the task screen;
     - a plain-task run line shows "Task", the state and Stop, with no step and no Continue.
   - Then the button, the `NewTaskDialog` initial values (or a thin wrapper), and a
     `startTask(itemId, …)` in the workflow runs' API service and state. Views do not call the API
     directly.
4. **E2E and docs.**
   - A Playwright spec (fake agent, in-memory backlog):
     - start a task on an item, then check the card, the task screen and the item link;
     - Stop, and the buttons are back;
     - the card's lane never changes.
   - The README API section gets the new endpoint.
