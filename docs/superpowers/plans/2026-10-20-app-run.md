# Apps in a task — Implementation Plan (pathfinder-dev-ui)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Light format: each task gives
> goal, files, interfaces, behaviours (tests to write first) and pitfalls; write the code against the real files.

**Goal:** the Docker launcher publishes each task's app ports; the API relays app control to the bridge; the task
view shows the apps with Open, Logs, Restart, Stop or Start — in this app's existing look.

**Spec:** `docs/superpowers/specs/2026-10-20-app-run-design.md`; the bridge side is
`../pathfinder-dev-base/docs/specs/2026-10-20-app-run-design.md` (label `agentic.apps` = base64 JSON
`{name: {ports, url, autostart}}`; bridge routes `GET /apps` → `[{name, state, ports, url, since}]`,
`POST /apps/:name/start|stop|restart` → 202 app, `GET /apps/:name/logs?lines=N` → `{lines}`; event `app`
`{name, action, exit_code}`).

**Where:** `C:\Work\Pathfinder-Oficial\pathfinder-dev-ui`, local branch `feat/app-run`. Run in WSL at
`/mnt/c/Work/Pathfinder-Oficial/pathfinder-dev-ui` (`npm test`, `npm run lint`, `npm run test:e2e`), every call in
`timeout`. The user's app runs from this checkout on port 3101 (`.local/3101`): never stop or restart it, never
`npm run build` into `dist/` while it runs (use the test configs, which do not need `dist`, or a copy).

## Global Constraints

- This repo's CLAUDE.md layering: api → service → integration/repository → commons; the engine only through
  `engine/index.ts`; frontend views → state → api; boundary specs must still pass.
- **Do not change the app's design or colours.** Use existing components (`Button`, `StatePill`, `FactsPanel`, …)
  and CSS modules; new CSS only for layout of the new section, using existing variables; no new colours.
- No token in labels, responses or logs; bridge errors map through `bridge-error.filter.ts`.
- Local commits only, no attribution lines; never push; never touch the user's containers or `~/work`.

## Review Focus

- An image without the label, or with a malformed one — the task starts with no apps, never fails.
- A port already used on the host — Docker picks a random host port, so two tasks with the same app both start.
- A task started before this change (no `appPorts` in its record) — apps list without links, no crash.
- A local-launcher task — the section says "Apps need the Docker launcher"; the API answers 409.
- App names with special characters in the URL — validated before any bridge call.

### Task 1: Ports in the Docker launcher

**Files:** `backend/src/engine/integration/launcher/docker-task-launcher.ts`, the launcher interface and task record
types in `backend/src/engine/service/`, `task-record.repository.ts` if the record shape changes, tests under
`backend/test/unit/engine/`.

**Behaviours (tests first):** label parsed (invalid → no apps, logged once without values); `ExposedPorts` and
`HostConfig.PortBindings` `{"<port>/tcp": [{HostIp: "127.0.0.1", HostPort: ""}]}` per app port; after start the
container's `NetworkSettings.Ports` gives the host ports, stored as `appPorts: {name: {containerPort: hostPort}}`;
the local launcher returns no `appPorts`; a resumed task keeps its ports (Docker keeps bindings on restart).

### Task 2: Bridge client, service and API routes

**Files:** `backend/src/engine/service/bridge-client.ts` (interface), `backend/src/engine/integration/bridge/
http-bridge-client.ts`, the tasks service, `backend/src/engine/index.ts`, `backend/src/api/tasks/*` (controller,
DTOs), the fake bridge in `backend/test/helpers`, tests unit + `backend/test/e2e/*.e2e-spec.ts`.

**Behaviours (tests first):** `GET /api/tasks/:id/apps` → `[{name, state, ports, url, link}]` with
`link = http://localhost:<hostPort><url>` for the first port (null without a host port); start/stop/restart relay
and return the app; logs `lines` 1–2000 (400 outside); name `^[a-z][a-z0-9-]{0,30}$` (400 otherwise); a task stopped
via `/stop` → 409; a local-launcher task → 409 "apps need the Docker launcher"; bridge 404/409 pass through; the task
token never appears in a response.

### Task 3: The task view's apps section

**Files:** `frontend/src/api/models.ts`, `frontend/src/api/tasks-api.ts`, `frontend/src/state/*` (app list per task,
refetched on an `app` event from the task events stream), `frontend/src/views/TaskView.tsx` (+ a small `AppsSection`
view if cleaner, with its CSS module for layout only), tests in `frontend/test/` (jsdom).

**Behaviours (tests first):** per app: name, `StatePill` for running/stopped/failed, link `localhost:<port>` opening
in a new tab with `rel="noopener noreferrer"`, Buttons Logs, Restart, Stop when running or Start when stopped; Logs
shows the lines as text in a monospaced block; an `app` event refreshes the list; errors show as the view shows
other errors; nothing renders for a task without apps; the local-launcher message.

**Pitfalls:** read `TaskView.tsx` and `FactsPanel.tsx` first and copy their structure and classes; no new colours.
